# 02 调用流程、动态决策与技术取舍

## 调用流程

```text
CLI 问题
  → DeepSeek Chat Completions（或明确的 OFFLINE_MOCK）
  → 模型选择工具及参数
  → 程序验证参数、执行只读工具、记录 Trace
  → 工具结果返回模型，模型继续选择
  → submit_answer
  → 程序校验已读原文、逐字引文、同主题资料和冲突
  → 输出答案 / 冲突 / 不足 / 故障 / 未完成
```

可选工具：`search_docs`、`read_doc`、`check_conflicts`、`submit_answer`。模型选动作，工具执行骨架是固定的。正常请假问题可走“检索—读 L01—回答”；一般报销问题应走“检索—读 D01—读 D02—核对冲突—追问”。这是两个不同的工具路径。若模型提前提交答案，程序的引用和冲突校验会拒绝并返回可见错误，允许模型调整下一步。

## 数据与证据

`data/documents.json` 含 `id/title/version/scope/status/supersedes/sections/claims`。`sections.text` 是可引用的原文；`claims` 是为了演示可复查冲突而人工整理的结构化声明，加载时验证声明引文确实在原文中。检索使用标题三倍权重和正文字符二元组重合计分，适合本题少量中文资料；它没有语义理解能力。`check_conflicts` 只对相同主题、相同范围且数值不同的声明给出冲突；未提供显式替代关系时不会因日期较新自动决定优先级。

## 答案护栏

确定性回答必须至少检索一次、读取被引用文档、逐字引用真实片段。若检索命中的同主题文档有多份，必须全部读取并完成冲突检查。冲突结论必须引用冲突双方。资料不足可以说明缺口，工具运行故障与资料不足分开。当前护栏校验引用存在性和冲突条件，无法完全自动证明答案的语义蕴含；这是已知边界。

## 运行与工程边界

默认 9 次模型决策、12 次工具调用，避免无限循环及费用失控。模型 API 故障被归为 `model_error`，只对 429 和常见 5xx 进行一次短暂重试；不记录 Authorization 头或密钥。`--fail-tool` 只用于本地故障演示。数据均为只读合成资料，无写入外部系统的工具。

## 技术取舍

选择 Python 3.11 标准库、直接 HTTP 适配 DeepSeek 接口、`unittest` 和 JSON 文件，降低安装和复现门槛。模型名及 API 地址通过环境变量配置。当前官方接口支持 Chat Completions 函数调用；具体型号与特性可能更新，运行前以 [DeepSeek 官方文档](https://api-docs.deepseek.com/api/create-chat-completion/) 和账号控制台为准。
